This section lists all updates associated with version 8.19.38 of the Fleet integration Prebuilt Security Detection Rules.

Rule Description Status Version

Java HotSpot Fatal Error Log Created

Identifies the creation of a Java HotSpot fatal error log by a Java process. The JVM writes "hs_err_pid*.log" after a fatal error, such as an access violation, segmentation fault, or unrecoverable native-code failure. This may indicate an unsuccessful attempt to exploit a Java memory-corruption vulnerability. In particular, failed Java4Shell (CVE-2026-114938) heap-grooming or corruption attempts may crash the JVM before remote code execution succeeds. This event indicates a JVM crash and possible exploit attempt; it does not by itself establish successful exploitation or remote code execution.

Entra ID FIDO2 Passkey Registered Outside the Self-Service Portal

Identifies the registration of a FIDO2 or passkey authentication method for a Microsoft Entra ID user that was not initiated by the self-service combined registration portal (Microsoft App Access Panel), My SignIns or My Profile. Registration through Microsoft Graph, a service principal, or another application can indicate scripted provisioning with tooling such as DSInternals.Passkeys or roadtx, which adversaries use after account takeover to register a shadow passkey for phishing-resistant persistence. Administrative provisioning on behalf of users follows the same path and should be baselined.

GitHub Actions Workflow Run Rapidly Deleted

Detects when a GitHub Actions workflow run is deleted within 30 minutes of its creation. Adversaries who abuse Actions for execution or secret theft may delete short-lived runs afterward to remove job logs that show the malicious steps.

GitHub Activity from Credential Scanner User Agent

Identifies GitHub audit activity from a user agent associated with credential-scanning and secret-harvesting tooling such as TruffleHog or Nord Stream. These tools walk repository contents and API routes to locate hardcoded secrets, tokens, deploy keys, and other credentials. Legitimate users rarely drive GitHub API traffic with these user agents, so a match is a strong signal that an adversary or an unsanctioned scan is mining the organization for exposed credentials, frequently as a precursor to credential access and data collection from code repositories.

GitHub Repo Created

Identifies the creation of a GitHub repository by a non-bot actor. Unexpected repository creation can indicate unauthorized infrastructure setup, data staging, or misuse of a compromised GitHub account.

GitHub Exfiltration via High Number of Repository ZIP Downloads

Detects a high number of GitHub repository ZIP archive downloads by a single non-bot user from one source IP within a short window. The repo.download_zip action retrieves a full repository archive over HTTP, so adversaries use it to collect source code without a git clone (which clone-threshold rules watch), including with classic PATs, fine-grained PATs, or OAuth tokens. Grouping by actor and source IP and requiring a high archive-download count separates bulk source collection from occasional developer downloads.

new

1

GitHub Repository Transferred Out of Organization

Identifies when a GitHub repository is transferred out of an organization. A repository transfer moves the source code, issue history, pull requests, wikis, and settings to another user or organization and removes it from the originating organization’s control. Adversaries who have compromised a privileged account or token use outgoing transfers to move intellectual property to an account they control, making this both a collection and an exfiltration technique that can bypass controls focused on cloning or archive downloads.

new

1

GitHub Organization Removed or Transferred from Enterprise

Identifies when a GitHub organization is removed from an enterprise or transferred to another enterprise. Removing an organization takes its repositories, members, audit history, and billing out of the enterprise’s centralized management and security monitoring, while a transfer hands the organization and its repositories to a different enterprise or owner. An adversary with enterprise owner access can use either action to move intellectual property beyond the organization’s visibility or to disrupt the enterprise’s governance and security controls.

new

1

GitHub Payment Method Removed

Identifies the removal of a payment method from a GitHub organization or enterprise. Billing changes are high-privilege actions, and an adversary with billing-manager or owner access can delete a payment instrument to disrupt the organization’s paid plan, which can lead to downgraded features, suspended private repositories, and loss of access to paid capabilities. The action may also be used to obscure fraudulent plan changes or to pressure the organization during an extortion or takeover scenario.

1

GitHub Token Activity from Unusual User Agent

Identifies the first time a GitHub token is used with a given user agent to perform a clone, push, archive download, or API request. The rule tracks new combinations of user.name and github.user_agent over a 14-day history and covers classic personal access tokens, fine-grained personal access tokens, and OAuth access tokens. A token that suddenly authenticates from a new client is a common indicator of a stolen or misused credential, since an adversary replaying a token rarely reproduces the victim’s original tooling. Named credential scanners such as TruffleHog or Nord Stream are covered by a dedicated rule; this rule surfaces the broader set of first-seen clients, including generic libraries like python-requests.

new

1

GitHub Sign-in from Unrecognized Device

Identifies a GitHub sign-in from an unrecognized device. GitHub emits "user.sign_in_from_unrecognized_device", "user.sign_in_from_unrecognized_device_and_location", and "user.new_device_used" when an account authenticates from a device or location it has not seen before. For Enterprise Managed User (EMU) enterprises these user security-log actions stream into the enterprise audit log, where a sign-in from an unfamiliar device can indicate that stolen credentials or a hijacked session are being used from attacker infrastructure. Personal-account enterprises typically retain these events only in the per-user security log, which does not stream to Elastic, so this rule is targeted at EMU audit data.

new

1

GitHub Actions or Integration Secret Created

Identifies the creation of a GitHub Actions, Dependabot, or Codespaces secret at the organization, repository, environment, or user scope. Secrets are injected into CI/CD workflows at runtime, so an actor with write or admin access can create a secret to establish durable access or to stage credentials that workflows will consume, allowing malicious automation to persist even after the initial access path is closed. This technique has been observed in software supply-chain attacks such as Shai-Hulud. Because creating secrets is also routine for platform and deployment teams, this rule works best as a building block correlated with the actor, the token used, and any surrounding workflow changes.

new

2

GitHub Outside Collaborator Added to Repository

Identifies an outside collaborator being added to a GitHub repository. An outside collaborator is an individual account that is not a member of the organization but is granted direct access to one or more repositories. An attacker who has compromised an account or token can add a collaborator they control to retain access to private source code after the original credential is revoked, bypassing organization SSO and team-based review. This is distinct from adding an organization member (org.add_member), which is covered by a separate rule.

new

1

GitHub SSH or Deploy Key Added

Identifies the addition of an SSH public key to a GitHub user account or a deploy key to a repository. These keys grant Git access over SSH, so an adversary can add one to maintain persistent repository access after the original password, session, or token is revoked. Note that a user-level public_key.create action may not appear in a non-EMU enterprise audit stream, where it is retained only in the per-user security log.

new

1

Kubernetes Pod Creation Using Common Debug or Base Images

Detects successful Kubernetes pod creation requests using commonly abused base and debugging container images such as BusyBox, Alpine, Ubuntu, Netshoot, and network multitool variants, as well as container runtime and image-build images such as Docker-in-Docker (dind), Podman, BuildKit, Buildah, and Kaniko. Base and debug images are frequently used by attackers to deploy short-lived or interactive "throwaway" containers for reconnaissance, payload staging, or command execution. Container runtime and build images are used to run nested containers or build images on-host, bypassing registry-based image controls. This is a New Terms rule that surfaces the first time a given source, user agent, and user deploy such an image within the lookback window.

new

5

Shell Evaluated Curl Downloaded Content

Detects a shell that downloads content with curl and passes it to eval, either directly or through a variable assignment. Downloading a script and evaluating it in memory avoids writing the payload to disk and is commonly used by macOS loaders, adware and infostealer stagers to retrieve and run their next stage.

new

1

SUID/SGID Bit Set

An adversary may add the setuid or setgid bit to a file or directory in order to run a file with the privileges of the owning user or group. An adversary can take advantage of this to either do a shell escape or exploit a vulnerability in an application with the setuid or setgid bit to get code running in a different user’s context. Additionally, adversaries can use this mechanism on their own malware to make sure they’re able to execute in elevated contexts in the future.

Entra ID Register Device with Unusual User Agent

Detects successful, user-initiated Microsoft Entra ID audit events for Register device where additional details indicate an Azure AD join or Azure AD register and the recorded user agent is not one of the common native registration clients (Dsreg, DeviceRegistrationClient, or Dalvik-based Android enrollment). Legitimate Windows and standard mobile enrollment flows present predictable user-agent strings; unexpected clients such as axios, node, python-requests, or offensive tooling like GraphSpy and ROADtools may reflect scripted or adversary-driven device registration used to obtain a Primary Refresh Token for persistence or token abuse. Registrations performed by service principals or the Device Registration Service itself (for example Windows 365 Cloud PC pre-authorized joins) and Microsoft-owned EvoSTS authorization checks are excluded. Baseline approved provisioning tools and MDM integrations before tuning.

3

Entra ID Device Registration with ROADtools Default OS Build

Identifies a Microsoft Entra ID device registration where the recorded cloud device operating system build is "10.0.19041.928" and the device display name follows the default "DESKTOP-" pattern. This combination is the default device profile that ROADtools (roadtx) uses when registering a device, and it is uncommon for the OS build to match the hardcoded value across an environment of otherwise patched hosts. Adversaries register rogue devices in Entra ID to acquire a Primary Refresh Token (PRT), establish persistence, and obtain trusted, programmatic access to the tenant. Because the OS build is a tool default, this is a high-fidelity but evadable indicator; baseline approved provisioning tooling and device naming conventions before relying on it. This rule also flags a device registration via Windows Hello for Business (WHfB) whose user agent carries the ROADtools hardcoded Dsreg build "10.0.19044.1826" ("Dsreg/10.0 (Windows 10.0.19044.1826)"), which is a separate tool tell from the device OS build and survives a change to the registered OS version or device name.

Entra ID Unusual Cloud Device Registration

Detects a sequence of Microsoft Entra ID audit events indicative of cloud device registration using the default device profile of ROADtools (roadtx). The sequence begins with an "Add device" operation from the Device Registration Service where the user agent is "Microsoft.OData.Client/*", the recorded cloud device OS build is a ROADtools default ("10.0.19041.928" or "10.0.19045.2006") and the display name follows the default "DESKTOP-" pattern, followed within the same correlation ID by "Add registered users to device" or "Add registered owner to device", which completes the registration and binds the device to a user. This flow is used to establish persistence or acquire a Primary Refresh Token (PRT). The OS build and naming are tool defaults, so this is a high-fidelity but evadable indicator.

Kubernetes Pod Created With HostNetwork

This rules detects an attempt to create or modify a pod attached to the host network. HostNetwork allows a pod to use the node network namespace. Doing so gives the pod access to any service running on localhost of the host. An attacker could use this access to snoop on network activity of other pods on the same node or bypass restrictive network policies applied to its given namespace.

Kubernetes Privileged Pod Created

This rule detects when a user creates a pod/container running in privileged mode. A highly privileged container has access to the node’s resources and breaks the isolation between containers. If compromised, an attacker can use the privileged container to gain access to the underlying host. Gaining access to the host may provide the adversary with the opportunity to achieve follow-on objectives, such as establishing persistence, moving laterally within the environment, or setting up a command and control channel on the host.

212

M365 Exchange Mailbox Items Accessed Excessively

Identifies an excessive number of Microsoft 365 mailbox items accessed by a user either via aggregated counts or throttling. Microsoft audits mailbox access via the MailItemsAccessed event, which is triggered when a user accesses mailbox items. If more than 1000 mailbox items are accessed within a 24-hour period, it is then throttled. Excessive mailbox access may indicate an adversary attempting to exfiltrate sensitive information or perform reconnaissance on a target’s mailbox. This rule detects both the throttled and unthrottled events with a high threshold.

Unusual SSHD Child Process

This rule detects the creation of an unusual SSHD child process through the usage of the "new_terms" rule type. Attackers may abuse SSH to maintain persistence on a compromised system, or to establish a backdoor for remote access, potentially resulting in an unusual SSHD child process being created.

Quarantine Attrib Removed by Unsigned or Untrusted Process

Detects deletion of the quarantine attribute by an unusual process (xattr). In macOS, when applications or programs are downloaded from the internet, there is a quarantine flag set on the file. This attribute is read by Apple’s Gatekeeper defense program at execution time. An adversary may disable this attribute to evade defenses.

update

118

First Time Python Spawned a Shell on Host

Detects the first time a Python process spawns a shell on a given host. Malicious Python scripts, compromised dependencies, or model file deserialization can result in shell spawns that would not occur during normal workflows. Since legitimate Python processes rarely shell out to interactive shells, a first occurrence of this behavior on a host is a strong signal of potential compromise.

Persistence via Suspicious Launch Agent or Launch Daemon

Identifies the creation of a launch agent or daemon property list file containing abnormal or suspicious values. An adversary may establish persistence by installing a new launch agent or daemon which executes at login. This rule looks for plist files created in LaunchAgents/LaunchDaemons directories with paths commonly used by malware.

PKINIT Followed by Same-Principal U2U Service Ticket

Identifies a successful PKINIT ticket-granting ticket request followed within five seconds on the same domain controller and source address by a successful user-to-user service-ticket request whose service SID matches the PKINIT principal SID. This sequence is consistent with the KDC-visible ticket requests used in an UnPAC-the-Hash attack, before client-side PAC credential decryption and NT hash recovery. The certificate used for PKINIT may have been obtained through CertiGhost or another certificate-abuse path.

System Public IP Discovery via DNS Query

Identifies DNS queries to known public IP address lookup web services from suspicious Windows processes, which can reveal external IP or internet-connectivity discovery before follow-on activity.
