Kubernetes Pod Creation Using Common Debug or Base Images

edit

Detects successful Kubernetes pod creation requests using commonly abused base and debugging container images such as BusyBox, Alpine, Ubuntu, Netshoot, and network multitool variants, as well as container runtime and image-build images such as Docker-in-Docker (dind), Podman, BuildKit, Buildah, and Kaniko. Base and debug images are frequently used by attackers to deploy short-lived or interactive "throwaway" containers for reconnaissance, payload staging, or command execution. Container runtime and build images are used to run nested containers or build images on-host, bypassing registry-based image controls. This is a New Terms rule that surfaces the first time a given source, user agent, and user deploy such an image within the lookback window.

Investigating Kubernetes Pod Creation Using Common Debug or Base Images

This rule identifies successful, first-seen pod deployments that use commonly abused troubleshooting, base, container-runtime, or image-building images, which can signal unauthorized execution or attempts to bypass image controls. An attacker may launch a short-lived BusyBox or Netshoot pod to enumerate cluster services and stage commands, or deploy a nested-container image to build and run unapproved workloads directly within the cluster.

Possible investigation steps

  • Attribute the request to a workload or human owner and confirm the namespace, service account, source address, authentication method, and change ticket are expected.
  • Review the complete pod specification for interactive commands, privileged mode, added capabilities, host namespaces, hostPath mounts, sensitive environment variables, and access to secrets or high-privilege service accounts.
  • Validate the image registry, repository, tag, digest, signature, admission-policy result, and vulnerability scan against approved debugging or build workflows.
  • Correlate nearby audit activity from the same identity and source for secret access, discovery, exec or attach sessions, privilege changes, workload creation, and rapid pod deletion.
  • Preserve pod logs, events, runtime telemetry, and network connections, then isolate or remove the pod and revoke exposed credentials if the deployment is unauthorized.

False positive analysis

  • An authorized administrator may create a short-lived BusyBox, Alpine, Ubuntu, Netshoot, or network-multitool pod for troubleshooting; verify the user, namespace, source address, pod commands, and associated change record.
  • An approved build workflow may create a pod using Docker-in-Docker, Podman, BuildKit, Buildah, or Kaniko; confirm the service account, image registry and digest, pod configuration, and expected build activity.

Response and remediation

  • Isolate the malicious pod by applying a deny-all network policy or quarantining its namespace, then suspend the responsible service account and preserve the pod specification, logs, events, and container runtime evidence.
  • Delete unauthorized pods, controllers, jobs, cron jobs, daemonsets, role bindings, admission webhooks, and nested-container or image-building artifacts created by the attacker.
  • Revoke and rotate exposed service-account tokens, registry credentials, secrets, cloud credentials, and node credentials, and terminate active exec, attach, or port-forward sessions.
  • Rebuild affected workloads or nodes from trusted images and declarative manifests, verify image digests and signatures, and confirm that no unauthorized containers, hostPath mounts, privileged settings, or modified resources remain.
  • Escalate immediately to incident response if the pod accessed secrets, used privileged or host-level access, contacted external infrastructure, created additional workloads, or affected multiple namespaces or nodes.
  • Prevent recurrence by enforcing approved registries and signed images, restricting debug and build images, denying privileged pods and risky host mounts, applying least-privilege RBAC, and alerting on unusual pod creation and exec activity.
